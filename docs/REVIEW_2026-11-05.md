# Go2 自主导航工程 review · 2026-11-05

用户反馈：可以站立、遥控；自主导航不走或走走停停。

结论：工程已经具备传感器、LIO、定位、规划、执行桥等模块，但还没有形成可重复验收的自主导航闭环。当前应先修复控制与数据有效性契约，再验证单目标导航。继续增加巡检功能或叠加经验阈值，难以定位问题。

本次审查覆盖工作区源码、启动脚本、关联的 Point-LIO / SCAN-Planner 核心、历史日志及本机 Docker 状态；执行了无 ROS、无 SDK 的纯方法复现。未连接 Orin 核对部署副本，未重启容器或向机器人发送指令。下述历史日志不能替代当前真机状态，代码缺陷也不能直接证明某次现场停走的唯一原因。

## 按优先级排序的代码问题

### R1 · P1：斜装雷达的水平距离算短，导致过早拦截

位置：`obstacle_veto.py:178–184`。

`vh` 已投影到地面切平面，但坐标仍在倾斜的传感器坐标系中。随后使用 `hypot(vh.x,vh.y)` 丢弃了有效的 z 分量。当前先验约 47° 倾角，前向距离被压缩到约 0.680 倍。

纯方法复现：构造离地 0.40m、距 `body_c` 前方 1.20m 的点，当前 `_ingest` 返回 `0.8162559m`，因此进入前方 1m 拦截区。实际前向拦截边界约扩大到 1.47m。这足以解释部分“前面明明还有空间却停下”的情况，现场占比仍需同步记录验证。

修复方向：使用 `hypot(vh @ f, vh @ l)` 或三维范数，并统一 `near_keep / sector_r / ring_r / touch_r` 的距离定义。以多倾角、多方位、已知物理距离作为回归用例，不能靠缩小阈值补偿公式错误。

### R2 · P1：否决层会放大速度，且不能解决净空处的起步死区

位置：`obstacle_veto.py:262–271`；控制器：`/home/mu/workspace/SCAN-Planner/standalone/src/scan_planner.cpp:978–995`。

当前仅在出现障碍并消解分量后，把残速抬到 `v_min_walk=0.25`。纯方法复现：输入前向 `0.05m/s`，空旷处输出仍为 `0.05`；在 45°、0.5m 障碍条件下，输出约 `(0.1768,-0.1768)m/s`，合速度成为 `0.25`，是输入的五倍。

这同时破坏上游慢速/减速意图，又没有解决空旷处的小速度无法起步。`creep_test.py` 注释记载 0.20–0.25m/s 起步门限，但本次没有重新验证真机门限，不能把它当成跨模式、跨方向的常量。

修复方向：起步、停步迟滞与最小可执行速度归控制器/运动适配器管理；适配后再进入最终否决层。否决层不增加平动速度模长。最小版本可先采用保守停车策略，保留滑行必须检查所有相关障碍约束。

### R3 · P1：传感器“刚收到”被当作“刚采集”

位置：`obstacle_veto.py:192–205,230–240`。

`on_cloud` 只检查点数、格式和散布，收到就刷新 `last_fresh_t`；完全不检查 `header.stamp`、时间戳是否前进、采集年龄。旧帧在队列中延迟到达、重复帧持续到达时，会不断重新获得 1 秒有效期。

纯方法复现：2000 点、散布有效、`header.stamp.sec=1` 的点云仍把 `fresh_frames` 增为 1，并把接收年龄刷新到接近零。即使相同帧重复到达，当前也没有序列/时间戳去重。

修复方向：区分采集时间、接收时间、处理时间；明确雷达时钟与 ROS 时钟映射后，同时限制采集年龄、接收间隔和时间戳前进性。跨设备钟差未校准时不能直接做 epoch 相减；回放模式须有独立时钟策略。命令输入目前复用 depth=10 的 QoS，也与“最新指令 depth=1”的注释不一致。

### R4 · P1：停车指令和速度指令共用可覆盖槽位

位置：`go2_bridge.py:113–141`。

`_on_cmd('stop')` 和 `_on_cmd_vel` 都写同一个 `_pending`。如果工作线程取走停车前下一帧速度到达，停车命令就被替换。即使 StopMove 已调用，持续速度流也能立即重新启动运动。

纯方法复现：先输入 stop，队列为 `('cmd','stop')`；紧接着输入速度，队列变成 `('move',0.05,0,0)`。

修复方向：停车/撤销使能拥有独立高优先级和锁存状态；未明确重新使能前持续速度流不能恢复运动。RPC 使用有界超时，停车/看门狗不能依赖一个可能被其他 RPC 长时间占用的执行路径。状态同时报告接收、发送和实际运动，`Move code=0` 仅能证明已发，不能证明狗已经执行。

### R5 · P1：定位失效没有进入规划准入，旧位姿可被无限外推

位置：`scan_planner_ros2/src/scan_planner_node.cpp:90–100,139–171`；`point_lio_ros2/src/map_localization_node.cpp:243–251,407–412,479–492,619`。

规划器只保留“曾经收到定位”的布尔值，没有定位/点云的超时和质量门控，也没有订阅 `/loc/health`。定位一旦断供，`loc_pos + loc_vel * interp_t` 可以持续增长；速度流仍在产生，桥的失联看门狗无法判断上游使用的是旧状态。定位节点在狗流缺席时不裁决；健康字符串默认 `OK`，且没有完整的 NO_DOG / STALE / LOST 语义。

另一个可确认的冻结问题：死推期间狗流断供，`publishDR(..., frozen=true)` 返回最初锚点 `T_mb_anchor_`，并非最后发布的死推位姿；狗在死推阶段已移动时，会回跳到锚点（`map_localization_node.cpp:328–331,481–484`）。

修复方向：定义可执行的健康状态和新鲜度契约；定位/点云超时立即阻止自主命令；外推有明确上限；冻结保持最后有效输出；质量恢复后重新建立目标执行条件。检查 LIO 质量门控后仍无条件发布位姿和点云的路径（`point_lio_node.cpp:694–750`），将质量状态传到下游。

### R6 · P1：避障结果没有回到控制器，轨迹时间继续推进

位置：`scan_planner_ros2/src/scan_planner_node.cpp:60–80,165–171`；`/home/mu/workspace/SCAN-Planner/standalone/src/scan_planner.cpp:965–995`。

ROS 包装只订阅定位、LIO、点云和目标，没有订阅 veto 状态或实际执行反馈。控制器仅在自身航向误差大时冻结轨迹时间；外部否决层把速度归零/改向时，轨迹仍按墙钟推进，位置误差继续积累。恢复放行后可能追赶已经推进的轨迹，引起再次拦截和反复重规划。

修复方向：增加 BLOCKED / STALE / STOPPED 的执行反馈；持续受阻应暂停轨迹进度、请求重规划或结束目标并给出原因。已有 `setExecutionFrozen` 面向内部航向控制，不能只从外部调用一次就假设完整解决；需要明确核心控制器与外部执行状态的所有权。

### R7 · P2：同一个 `body` TF 有两个父节点

位置：`point_lio_ros2/src/point_lio_node.cpp:805–816` 与 `point_lio_ros2/src/map_localization_node.cpp:450–477`。

默认同时发布 `camera_init→body`、`map→body` 和 `map→camera_init`，不满足 TF 树中单个 child 只有一个 parent 的要求。另外 LIO 的 body 实际对应雷达/IMU 坐标，而狗控制使用机体坐标，需要独立的安装外参。

修复方向：明确 `map→odom→base_link→lidar/imu` 的唯一发布者和外参约定；死推接管时保持同一条树。当前规划代码直接计算变换，因此不能把 TF 问题单独断言为全部停走的根因，但它会使 RViz 和后续 TF 消费者不可靠。

### R8 · P2：部署与回归入口已经分叉，缺少版本与结果闭环

位置：`live_stack_start.sh:6–13,25–46`；`orin_deploy/patrol_safety_start.sh:17–34`；`README.md:81–83`；`test_veto_offline.py:75–78,108–119`。

工作站启动只数进程，不验证 Orin relay/veto/桥、狗里程计、目标生效或消息新鲜度。生产代码、外部核心、Orin 副本分散，启动脚本依赖机器绝对路径和已编译静态库；两个核心仓库都有未提交修改。只记录 Git HEAD 不能复现当前版本。

README 中的旧离线回放流程没有启动 CustomMsg→PointCloud2 relay，当前 veto 默认订阅 `/livox/points2`，照旧文档可能一直 STALE。离线脚本发布 `/cmd_vel_raw`，只把 veto 输出 remap 到测试话题不能隔离其他同 domain 的真机订阅者。脚本只打印统计，收不到输出也直接 return，缺少失败退出码；固定 bag 回放也不能验证闭环车辆执行。

修复方向：固定源码+未提交补丁+二进制+配置+地图的部署清单；统一 test/live 入口，测试使用隔离 domain/网络和 mock 执行器；每轮输出机器可读结果和非零失败码。旧探针分类归档，保留原始证据。
